# Implementation Details

Each section covers one module: what its important functions do, why it was built that way, how it handles failure, and the trade-offs accepted.

## 1. Configuration: `lakehouse/config.py`

`Settings` (pydantic-settings) reads the environment and `.env`.
- **No credential defaults:** `source_db_url` and `warehouse_db_url` have no default. `require_databases()` (called by `pipeline.init`) raises `ConfigurationError` with a clear message instead of silently connecting to a guessed database.
- **Paths:** `bronze_root`, `silver_root`, `quarantine_root` and `metrics_root` are all derived from `LAKE_ROOT`.

## 2. Synthetic data: `lakehouse/generate.py`

`simulate(batch_date)` replays every day from `START_DATE` (2025-11-01) up to the batch, seeding each day with `random.Random(f"{SEED}-{index}")`. Generation is therefore a pure function of the date: any batch can be regenerated byte-identically (tested on the CSV bytes).

| Day | Generated |
|---|---|
| 0 | 40 products, 300 customers, ~3 months of orders (Aug–Oct 2025), 60 historical returns |
| k ≥ 1 | see list below |

For every later day:
- 12 customer changes (tier or city; these drive SCD2);
- 3–6 new customers;
- 2 price changes;
- 15–25 orders;
- 4 late status changes (completed → returned);
- one **late line item** added to an order 2–9 days old;
- one **late-arriving customer**, who orders today but appears in tomorrow's CRM export (`crm_visible_from`).

Injected defects for Silver to handle:
- exact duplicate customers;
- a row with a null key and a row with an invalid email;
- emails in mixed case with surrounding whitespace, and lower-case province codes;
- order status with odd casing (`" Completed "`) and channel in upper case (`IN_STORE`);
- a zero-quantity line item, a negative price and negative stock.

Business rules respected:
- orders only at stores that are already open (`STORE_OPENED`, enforced by a dbt test);
- orders only by customers who have already signed up.

`write_source_db` is idempotent. `sales.generator_log` records generated batches, and inserts use `ON CONFLICT DO NOTHING`.

## 3. Bronze: `lakehouse/bronze.py`

- **`compute_window(batch_date, previous)`** is a pure function that decides the incremental extraction window:
  - **re-run of a known batch:** reuse its original window, so the same rows are extracted again;
  - **new batch:** start at the latest *succeeded* earlier batch's end, so a failed batch's data is caught up automatically, and end at `D 00:00`;
  - **a window that would go backwards:** raise an error.
- **`register_batch`:**
  - refuses with `OutOfOrderBatchError` if any *later* batch has already succeeded. Customers and products are full snapshots, so replaying an old batch would roll the warehouse's current state back in time;
  - otherwise upserts the batch row with `status='running'`.
- **`ingest_csv`:** reads with `dtype=str, keep_default_na=False`, so values like `"NA"` survive. Bronze is raw; typing happens in Silver.
- **`ingest_postgres`:** `updated_at > start AND updated_at < end`, then everything is cast to strings.
- **`_write_partition`:** deletes and rewrites `batch_id=DATE/`, so re-running a batch is idempotent.

## 4. Silver: `lakehouse/silver.py` (PySpark)

Each `clean_*(df) -> (valid, rejected)` is a pure DataFrame transformation (unit-tested with a local Spark session).

| Step | Implementation |
|---|---|
| Normalise | `_blank_to_null` (trims; `""` → NULL), `lower`/`upper`/`initcap`, status aliases via `create_map` (`complete` → `completed`, `canceled` → `cancelled`), channel `-`/space → `_` |
| Enforce schema | Explicit casts: `long`/`int`, `DecimalType(10,2)` for money, `DecimalType(5,2)` for %, `to_date`, `to_timestamp`. With `spark.sql.ansi.enabled=false`, malformed values become NULL and fail a rule instead of crashing the job |
| Validate | `_apply_rules`: an ordered list of (name, condition). `_reject_reason` is the *first* failing rule. `coalesce(cond, false)` treats NULL as a failure |
| Deduplicate | `_dedupe`: `row_number()` over the business key, ordered by `updated_at DESC`, **then every other column** as a tie-break, so the survivor is deterministic even for exact duplicates |
| Account | `EntityMetrics`: bronze = quarantined + duplicates removed + written (checked by reconciliation) |

Writes (`process_entity`):
- **customers, products:** `replace_dataset`, which writes to a staging directory and swaps it in;
- **inventory:** `overwrite_partitions` on `snapshot_date` (dynamic partition overwrite);
- **orders:** `upsert_parquet` by `order_id`, partitioned by `order_month`;
- **order_items:** `upsert_parquet` by `order_item_id`.

`get_spark` pins `PYSPARK_PYTHON` to the driver's interpreter. Without that, workers ran a different Python and failed with `PYTHON_VERSION_MISMATCH`.

## 5. Parquet merge: `lakehouse/merge.py`

`upsert_parquet(spark, updates, target, keys, order_by, partition_cols)`:
1. Reads the existing data. With partitions, it keeps only the partitions touched by the update (`left_semi` join).
2. Unions it with the updates, tagged `_incoming = 1`.
3. Takes `row_number` over the keys, ordered by `order_by DESC` then `_incoming DESC`, so the latest version wins and ties go to the incoming row.
4. Writes to `.target_staging_<uuid>`, then swaps the leaf partition directories (or the whole directory) into place.

Spark cannot overwrite a path it is lazily reading from, which is why the staging step exists. Stale staging directories from crashed runs are removed first.
- **Trade-off:** the swap is not atomic across partitions. On object storage, use Delta Lake or Iceberg `MERGE` instead; the semantics would be identical.
- **Tests:** a re-run is a no-op; stale updates lose; untouched partitions keep their files.

## 6. Quality gate: `lakehouse/quality.py` (Great Expectations 1.x)

- **Suites:** `suites(reference)` defines per-entity expectations tagged `critical` or `warning` (23 per batch). Examples: uniqueness, value sets, numeric ranges, regex emails, compound-key uniqueness, `unit_price > unit_cost` (warning), and foreign keys to Silver customers and products (warning).
- **Validation:** `validate_frame` runs an ephemeral GX context against the Silver rows of this batch (`_batch_id = D`).
- **The gate:** `run_quality` raises `DataQualityError` on any critical failure **or** when an entity's quarantine rate exceeds `MAX_QUARANTINE_RATIO` (5%). The gate runs **before** the load, so a bad batch never reaches the warehouse; the e2e test proves this with a fingerprint comparison.
- **Late-arriving customers are a warning, not a failure:** batches 2 and 3 pass 22/23 checks, the one non-pass being the warning-level customer foreign key.
- **Noise control:** GX progress bars and import-time logging are silenced, so Airflow logs stay readable.

## 7. Load: `lakehouse/load.py`

- **Snapshot entities:** `DELETE` + `COPY`.
- **Incremental entities:** `COPY` into a per-entity `TEMP TABLE … ON COMMIT DROP`, then `INSERT … ON CONFLICT (pk) DO UPDATE` with every non-key column.
- **Atomicity:** all five entities load in **one transaction**, so the warehouse never sees a half-loaded batch. The per-entity temp table name fixed a real collision bug.
- **What is loaded:** only the Silver rows whose latest version came from this batch (`_batch_id = D`).

## 8. dbt: `dbt/`

| Layer | Models |
|---|---|
| staging (views) | `stg_*`: renaming plus derived flags (`is_completed`, `below_reorder_point`); `line_revenue` from one macro (`macros/line_revenue.sql`) |
| snapshot | `customers_snapshot` (YAML config, `strategy: timestamp`, `updated_at`), so validity reflects CRM business time, not load time |
| marts | `dim_customers` (SCD2 + unknown member `-1`), `dim_products` (SCD1), `dim_stores` (seed), `dim_date`; facts below |
| reports (views) | daily sales, monthly category margin, customer lifetime value, revenue by tier at order time, reorder alerts, customer change history |

### `fct_orders` (incremental, `delete+insert`, `unique_key=order_id`)

Each run recomputes three sets of orders:
1. orders whose own `_batch_id` ≥ the fact's watermark;
2. **orders that received late line items** in the new batch;
3. **orders currently attributed to the unknown customer**.

Without (2), a late item left the order's revenue stale. Without (3), an order whose customer arrived a day late kept `customer_sk = NULL`. That failed the `not_null` test and halted the pipeline on realistic data; the e2e run of 2025-11-02 reproduced it before the fix.

`customer_sk` resolution, recorded in `customer_resolution`:
1. `point_in_time`: the version valid on `order_date`;
2. `first_version`: the order predates the customer's first CRM timestamp;
3. `unknown`: `'-1'`.

A singular test fails if any order stays `unknown` for more than 2 days.

### Tests (40 total)
- **Generic:** unique, not_null, accepted_values (using the dbt 1.10 `arguments:` syntax) and relationships.
- **Singular:**
  - SCD2: no overlapping versions, and exactly one current version per customer;
  - revenue reconciles with staging, and fact row counts match staging;
  - inventory grain is unique, and there is no negative revenue;
  - no orders before a store opened;
  - no stale unknown customers.

## 9. Reconciliation: `lakehouse/reconcile.py`

14 checks per batch:
- **Extraction completeness** (2): Bronze rows = source rows in the window, for orders and items.
- **Silver accounting** (5): bronze = quarantined + duplicates + written, per entity.
- **Load completeness** (5): Silver row count = `lake_silver` row count, per entity.
- **Revenue** (1): completed revenue recomputed in Python from Silver Parquet, with `Decimal` and half-up rounding to match the dbt macro, equals `sum(fct_orders.recognized_revenue)` within $0.01.
- **Dimension coverage** (1): current `dim_customers` rows (excluding the unknown member) = Silver customers.

Results go to `_metrics/.../reconciliation.json`. A failure raises `ReconciliationError`, and the batch is marked `failed`.

## 10. Pipeline and CLI: `lakehouse/pipeline.py`, `lakehouse/cli.py`

`run_batch` calls `init` (idempotent DDL) and then the seven steps, logging each step's duration.
- **On failure:** marks the batch `failed`, except for `OutOfOrderBatchError`, which is refused before any work and must not rewrite the history of an existing batch (a bug found and fixed during the audit).
- **CLI:** `cli.run` prints `ERROR (<Type>): <message>` to stderr and exits 1, so Airflow marks the task failed. `demo` runs N batches and then re-runs the last one.

## 11. Idempotency and recovery summary

| Scenario | Mechanism | Verified by |
|---|---|---|
| Re-run of the latest batch | window reuse, partition rewrite, upsert merge, ON CONFLICT load, dbt delete+insert | fingerprint of 9 warehouse tables identical (e2e + demo) |
| Re-run of an older batch | refused (`OutOfOrderBatchError`), status untouched | `test_rerunning_an_older_batch_is_refused` |
| Bad source file | GX gate fails before load, batch `failed` | fingerprint unchanged |
| Recovery after a bad file | source re-delivers, same batch re-run → `succeeded` | `test_quality_gate_blocks_bad_batch_and_recovers` |
| Batch never fixed | next batch's window starts at the last *succeeded* end | `test_failed_batch_data_is_caught_up_by_next_batch` |
| Late status change | extracted by `updated_at`, latest version wins | `test_late_status_change_updates_silver_and_fact` |
| Late line item | fct_orders reprocesses its order | `test_late_arriving_line_item_updates_earlier_order` |
| Late customer | unknown member, re-attributed next batch | `test_late_arriving_customer_is_reattributed` |
| Crash mid-merge | stale staging dirs cleaned on next write | code path in `_staging_path` |

## 12. Trade-offs

- **Plain Parquet** instead of Delta or Iceberg: there are no ACID guarantees across partitions; the staging swap is atomic per directory only.
- **Spark `local[*]`:** the data volume is a laptop's; the transforms are cluster-ready.
- **Snapshot entities replaced wholesale:** this is why backfilling older batches is refused rather than supported.
- **Day-grain SCD2 join:** an order on the same day as a customer change is attributed to the new version.
- **Single PostgreSQL** hosting both the source and the warehouse; plain environment-variable credentials.
